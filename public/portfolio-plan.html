02 — Positioning

The one sentence the whole site serves

Every section, every project card, every animation should be answering this. If something on the page doesn't support it, cut it.

A system developer who builds and maintains the web applications a federal agency runs on — Angular and ASP.NET in production, tested and documented, delivered with the people who use them.

What this rules out

No "creative developer" framing, no gradient blob hero, no 3D scene. Those signal a design-lead portfolio and would undersell what you actually do. You want a recruiter or hiring manager to close the tab thinking "this person can be handed a legacy module on Monday" — and to notice, secondarily, that the site itself is a well-built Angular app.

What this rules in

Precision. Evidence. Real numbers where you have them. Clean engineering visible in the source. A site that loads fast, works keyboard-only, and reads perfectly on a phone in a hiring manager's hand.

04 — Design direction

Technical documentation, treated with care

The concept: your portfolio should feel like a well-made engineering document rather than a marketing page. Confident typography, generous whitespace, a strict grid, monospace for metadata — and interactivity that demonstrates frontend skill instead of decorating.

Why this direction

It is native to who you are. You write UAT documents and architecture specs for a living; a portfolio in that register is authentic rather than borrowed. It also ages well, prints well, and — importantly — it is achievable to a high standard with CSS alone, so you spend your effort on execution instead of fighting a 3D library.

Colour

One accent, used sparingly, on a neutral that is tinted rather than pure grey. I'd suggest a cyanotype/blueprint blue — it connects to the documentation concept, reads as professional and technical, and avoids the two most over-used portfolio accents (neon green and violet gradients). A muted brass is the second accent for annotations and highlights only.

#0C1620Ink ground (dark)
#F2F5F8Paper (light)
#1A5C9EAccent — blueprint
#966A16Brass — annotation

This document is built in exactly that palette, so what you are reading is the direction rendered. Ship both themes with a toggle in the header — for a developer audience a dark mode is table stakes, and building it properly with CSS custom properties is itself a small competence signal.

Typography

Three faces, three jobs. Avoid Inter and Space Grotesk — they are the default choice in every AI-assisted portfolio this year and a hiring manager who has seen forty portfolios will recognise them instantly.

Display / headingsArchivo Semibold
Body / proseSource Serif 4 — set at 17px with generous leading for readable case studies.
Metadata / codeJetBrains Mono — ANGULAR · ASP.NET · APR 2026

The serif body is the deliberate risk here: almost no developer portfolio uses one, and it makes your case studies feel like documents worth reading rather than marketing copy. If it feels too editorial once built, swap the body face to Public Sans or Archivo at a lighter weight and keep everything else.

Type scale: 1.25 ratio. Body 17px / 1.68. Line length capped at 68 characters. Mono labels at 0.7rem with 0.12em letter-spacing, uppercase.

Layout & navigation

Grid

12-column, 1180px max, 24px gutters. Sections alternate between full-width and a 2-column split so the page has rhythm without needing decoration. Vertical spacing on an 8px scale.

Header

Slim, sticky, translucent on scroll. Left: MASZ monogram. Right: Work · Experience · About · Contact, theme toggle, CV button. Underline slides between items.

Section markers

Each section gets a mono eyebrow (01 — SELECTED WORK). Numbering is honest here because the home page is a fixed reading order.

Progress

A 2px scroll-progress rail under the header. Cheap to build, reads as engineered, and genuinely useful on a long home page.

Motion — five moments, no more

Restraint is the whole game. Scattered animation is the fastest way to look like a template.

  1. Load sequence. Hero elements fade and rise 12px, staggered 60ms apart. Once, on first paint.
  2. Scroll reveal. IntersectionObserver adds a class; 300ms fade + 12px rise. Never re-triggers on scroll back up.
  3. Project card hover. Screenshot scales to 1.03, the tech chips slide up from under the title, border shifts to the accent. One coordinated gesture, not three separate ones.
  4. Route transition. Angular's withViewTransitions() gives you a genuine cross-fade between home and a case study for one line of config.
  5. Skill ↔ project linking. The interactive idea below. This is the one place to spend real effort.

Everything wrapped in @media (prefers-reduced-motion: reduce). Durations 180–320ms, easing cubic-bezier(.2,.8,.2,1) — nothing slower, nothing bouncy.

Showing skills without a fake percentage bar

Do not use proficiency bars

"Angular 85%" is unverifiable and every experienced reviewer discounts it. Worse, it invites the question "85% of what?"

Replace it with something true and interactive: group skills by how you actually use them, and let each skill point at its evidence.

  • Three groups: Build (Angular, ASP.NET, C#, Laravel, PHP, TypeScript, SQL, Flutter) · Ship (Git, SDLC, UAT, system testing, deployment support) · Support (bug investigation, technical documentation, user access management, Power BI).
  • Each chip carries an honest context label instead of a number: production, professional, or academic. Angular is production · LGM. Flutter is academic · FYP. That is more informative than any bar and it is defensible in an interview.
  • The interaction: hovering or tapping a skill chip highlights every experience entry and project card on the page that used it, and dims the rest. It is a small piece of signal-driven state, it proves you can wire cross-component reactivity in Angular, and it turns the skills list into a navigation device. This is your one memorable interaction — build it well.

Experience without a wall of text

Your four roles carry twelve résumé bullets between them. Rendering all twelve is what makes portfolio sites unreadable. Structure each role as:

Row 1
Company · role · dates, on one line. Dates in mono, right-aligned, tabular figures.
Row 2
One sentence describing the mandate. Not a bullet — a sentence a human would say out loud.
Row 3
Up to three tech chips, and one outcome callout if you have a real one (e.g. the AJAX + SQL query work at Media Prima that improved data response time — quantify it if you can).
Row 4
A Details disclosure that expands the remaining bullets. Collapsed by default, animated height, fully keyboard-accessible.

Result: the section is scannable in fifteen seconds, and the depth is one click away for anyone who wants it. Present it as a vertical timeline with a hairline rule and small nodes — the upward trajectory from intern to officer is a story worth making visible.

Project card anatomy

Featured cards are full-width horizontal splits (visual left, content right, alternating sides). Secondary cards are a 3-up grid. Every card carries, in a fixed order:

  1. A mono index and a context chip (PROFESSIONAL / FINAL YEAR PROJECT / ACADEMIC) — sets expectations honestly before the reader judges the screenshot.
  2. Project name in the display face.
  3. One-line description — what it does and who for.
  4. Tech chips, maximum five.
  5. Two links: Case study → always; Code ↗ only where a real repo exists. An absent link is better than a link to an empty repo.

Card surface sits 1px above the ground with a hairline border, 4px radius — not the 16px pill radius that reads as a template. On hover the border takes the accent and a fine corner bracket draws in. Subtle, and it echoes the drafting-document concept.

Standing out without being flashy

Four things will do more for you than any effect:

  • Real content. Actual outcomes, actual constraints, actual screenshots. Most portfolios are 90% styling over 10% substance; yours can invert that.
  • A perfect Lighthouse run. 100/100/100/100 on a portfolio is a legitimate flex for a system developer, and you can put the score in the footer.
  • Full keyboard operability and visible focus rings. Almost nobody does this. It takes an afternoon and it is exactly the kind of care your UAT background implies.
  • A clean public repo for the portfolio itself — sensible commits, a real README, typed data. Reviewers will open it.

The one decision that keeps this maintainable

Content lives in typed TypeScript files, not in templates. Every project, role, and skill is an object in data/ conforming to an interface in models/. Adding a project later becomes one object, not a template edit. It also means the compiler catches a missing field before the browser does.

// models/project.model.ts
export interface Project {
  slug: string;                 // url segment
  name: string;
  tagline: string;              // one line for the card
  context: 'professional' | 'final-year' | 'academic' | 'client';
  tier: 'featured' | 'secondary' | 'archive';
  period: string;
  role: string;
  stack: string[];              // must match ids in skills.data.ts
  features: string[];
  outcomes?: string[];          // numbers where you have them
  media: { src: string; alt: string; kind: 'screenshot' | 'diagram' | 'wireframe' }[];
  repoUrl?: string;             // omitted when there is no repo worth linking
  confidential?: boolean;       // renders the "internal system" note instead of screenshots
}

Services — three, and only because they hold state across components

  • ThemeService — a signal for the current theme, written to localStorage, seeded from prefers-color-scheme, applied as data-theme on <html>. Wrap the storage read in try/catch.
  • SkillFocusService — a single signal<string | null>. The skills section writes to it; project cards and timeline items read it via computed() to decide whether they're dimmed. Roughly twenty lines, and it's the cleanest possible demonstration of signal-based cross-component state.
  • SeoService — sets Title and Meta (description, og:title, og:image) on each route. Matters when someone shares a project link.

No ContentService. With no backend, a service that returns a constant is indirection for its own sake — import the data array directly into the component. No state library. NgRx on a portfolio is a red flag, not a credential.

// app.config.ts
provideRouter(

In project-detail, resolve the slug against projects.data.ts and redirect to the 404 when nothing matches — so a stale link degrades properly.

Conventions worth committing to on day one

  • Standalone components throughout; no NgModules.
  • input() / output() signal APIs, not the decorators — your scaffold is zoneless, so signals are the path of least resistance.
  • @if / @for / @defer control flow. Use @defer (on viewport) for the heavy media on case-study pages.
  • NgOptimizedImage on every project screenshot — free lazy-loading and layout-shift protection, and it directly serves the Lighthouse goal.
  • Component-scoped CSS by default; only tokens and base styles are global.
  • Dependencies to add: none required. No UI kit, no animation library, no icon package — inline the six SVG icons you need. Every dependency you skip is a smaller bundle and a faster site.

Deployment

Static build, so anything works. GitHub Pages keeps everything on the profile a recruiter is already visiting; Netlify or Vercel give you a cleaner custom domain and deploy previews for free. Either way run ng build with prerendering so each route ships real HTML for search engines and link previews. Buy a domain — aimansyazwan.dev or similar — it costs about RM60 a year and it materially changes how the link reads on an application.

For the contact form: with no backend, either use a plain mailto: link (simplest, and honestly fine) or a third-party endpoint like Formspree or Web3Forms. Don't build a form that silently does nothing.

07 — Build order

Content first, chrome last

This order exists because the most common way portfolio projects die is styling an empty page for three weeks. Every step produces something you could ship.

  1. 01Write the contentFill data/ with real text for all seven projects and four roles — in a plain text file if that's easier. Nothing else can be designed accurately until this exists.
  2. 02Clear the confidentiality questionAsk LGM what may be published. Do this early — the answer changes what the two featured case studies contain.
  3. 03Gather visualsCapture KafaJr screenshots from an emulator; redraw the Media Prima data-flow diagram and the MSNR module diagram in Figma; export at 2× as WebP.
  4. 04Lay the design tokensWrite _tokens.css with both themes, plus base and typography. Build the ThemeService and toggle. Get this right once and every component after is easy.
  5. 05Shell and routingHeader, footer, four routes, lazy loading, view transitions, 404. Deploy this skeleton immediately so the pipeline is proven while it's still trivial.
  6. 06Home page top to bottomHero → featured work → experience → skills → about → beyond. Build the ui/ components as each section needs them, never speculatively.
  7. 07Projects list and case-study templateOne template that renders any project from its data object, with the confidential variant handled by a flag rather than a separate component.
  8. 08The skill ↔ project interactionYour signature moment. Build it only once the content is real, so you can see it actually working across the page.
  9. 09Motion passAdd the five moments from §04 in one deliberate sitting, then remove the two that add least. Verify reduced-motion.
  10. 10Polish and prove itLighthouse to 100, full keyboard pass, real-device check, meta tags and OG image, CV PDF in place. Then tidy your GitHub — README for KafaJr, private the scaffolds, delete the forks.
08 — Your call

Four things to confirm before we code

Everything above is a recommendation with a default. These four would change the build enough to be worth deciding deliberately.

1. Confidentiality on MSNR Trace 2.0 and the Media Prima dashboard

2. Serif body text

Recommended Source Serif 4 for prose. It's the choice that most distinguishes the site from every other developer portfolio, and it suits case studies. If you look at it and it feels wrong for a technical site, we swap to Public Sans and change nothing else.

3. Routed pages vs one long scroll

Recommended Routed, as specified. It costs little in Angular and gives you shareable per-project URLs — genuinely useful when applying for jobs. A single-scroll page is simpler but you lose that, and you lose the chance to show routing competence.

4. Scope of the first release

Recommended Ship §07 steps 1–7 as v1 — a complete, honest, well-built site — then add the skill-linking interaction and motion as v1.1. A live site with three real case studies beats an unfinished one with a beautiful hover effect.
